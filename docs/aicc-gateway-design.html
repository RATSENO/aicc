01배경 및 목적

렌탈 백오피스는 React 화면과, 주문 / 고객 / 상담 / 서비스 등 도메인별로 나뉜 Spring Boot MSA 앱들로 구성되어 있다. 지금까지는 상담사가 CTI로 전화를 받으며 이 화면을 직접 보고 조작해 업무를 처리해왔다.

이번 프로젝트는 AICC(챗봇/콜봇)를 도입해, 고객이 원하는 업무(예: "비데가 따뜻해지지 않는다" → AS접수) 중 일부를 상담사 개입 없이 봇이 직접 처리하도록 간소화하는 것이다. 대화 흐름과 의도 파악은 AICC 솔루션(외부 벤더)이 담당하고, 우리는 AICC가 백오피스 업무를 수행할 수 있는 API를 제공해야 한다.

기존 MSA를 벤더에 직접 노출하지 않고, 그 사이에 신규 중계 서버(AICC Gateway)를 두기로 했다 — 이 문서는 그 서버의 설계 논의를 정리한 것이다.

02전체 아키텍처

기존에 검증된 경로 / 메커니즘 신규 · 아직 확정되지 않음

핵심은 이거다 — 확정 상담app이 서비스app을 호출하는 등 기존 앱간 통신도 React 화면이 호출하는 것과 동일한 API를 공유해서 쓴다. 즉 "서버-서버 전용 내부 API"는 따로 없다. 그래서 Gateway도 별도 API가 아니라 이 화면용 API를 그대로 호출하게 된다.

03Gateway 내부 구조

시나리오가 AS접수 외에도 계속 늘어날 걸 전제로, 처음부터 시나리오별로 패키지를 분리해둔다. 특정 시나리오가 나중에 너무 커지면 그때 별도 앱으로 분리하면 된다.

aicc-gateway-service/          (신규 Spring Boot 앱)
 ├─ common/                    인증, 응답 포맷, 로깅, 예외처리
 │   └─ auth/                  시스템 계정 세션 관리 (05장 참고)
 ├─ client/                    기존 MSA 호출 전용 계층
 │   ├─ OrderClient
 │   ├─ CustomerClient
 │   └─ ConsultClient
 └─ scenario/                  "봇이 수행할 업무" 단위
     ├─ as/                    AS접수: 조회 → 확인 → 접수
     ├─ delivery/               배송조회 (예정)
     └─ cancel/                 해지 (예정)

client 계층을 분리해두는 이유는, 기존 MSA API 스펙이 바뀌어도 이 계층만 고치면 되고 시나리오 로직은 영향받지 않게 하기 위함이다.

04API 설계 원칙

화면 API가 아니라 업무 단위로

엔드포인트는 화면 구조가 아니라 "봇이 수행할 업무" 단위로 설계한다. 예: /api/aicc/v1/as/customer-lookup, /api/aicc/v1/as/tickets

Stateless 유지 확정

상담사 화면이 "이름 조회 → 고객 확인 → AS접수 생성"처럼 여러 단계를 거칠 때, 각 단계 API가 매번 필요한 정보를 파라미터로 전부 받는 방식이라는 게 확인됐다. 즉 서버가 "방금 조회한 고객" 같은 상태를 세션에 들고 있지 않는다. Gateway도 이 원칙을 그대로 유지한다 — 대화의 멀티턴 흐름(슬롯 채우기)은 AICC 벤더 쪽에서 관리하고, Gateway는 매 호출마다 완결된 파라미터를 받아 처리한다.

응답 포맷

필드용도
customerMessage봇이 TTS/채팅으로 그대로 읽어줄 고객용 문장
internalMessage내부 로그·디버깅용 상세 메시지 (고객에게 노출 안 함)
requiresHandoff봇이 처리 불가 → 사람 상담사 연결이 필요함을 나타내는 플래그
traceIdAICC가 발급한 대화/콜 세션 ID. 하위 MSA 호출까지 관통시켜 추적

공통코드 해석

기존 화면은 조회 API가 내려주는 고객유형코드: "1" 같은 코드값을, React가 별도의 공통코드 API로 "1" → "개인"을 매핑해 화면에 그려준다. AICC는 화면이 아니라 API 응답을 그대로 받기 때문에, 이 변환을 안 해주면 코드값의 의미를 알 수 없다.

Gateway가 이 변환 책임을 대신 진다. client 계층에서 조회 API 응답을 받은 뒤, 코드성 필드를 공통코드로 한 번 더 조회/캐시해서 라벨을 붙여 내려준다. 코드값과 라벨을 둘 다 포함한다 — 라벨은 고객에게 말해줄 때, 코드값은 시나리오 로직이 분기할 때(예: 법인 고객이면 담당자 연결) 쓰기 위함이다. 라벨 문구는 바뀔 수 있어도 코드값은 잘 바뀌지 않으므로 분기는 코드값 기준으로 한다.

{
  "customerTypeCode": "1",
  "customerType": "개인"
}

공통코드는 거의 바뀌지 않으므로, 매 요청마다 공통코드 API를 다시 호출하지 않도록 common/ 계층에 캐시(기동 시 로드 + 주기적 갱신)를 둔다. 시나리오별로 실제 어떤 공통코드 그룹이 필요한지는 09장의 "AS접수 상세 API 목록 확정" 작업 때 함께 조사한다.

Gateway는 판단하지 않는다

코드→라벨 변환(사전 찾아보기)과, 코드값에 따라 흐름을 가르는 판단/분기 로직은 구분해야 한다. 후자를 Gateway 코드 안에 복제하기 시작하면 07장의 DB 직접 접근과 같은 함정 — 백오피스 쪽 규칙이 바뀔 때마다 Gateway도 똑같이 고쳐야 하고, 안 그러면 조용히 어긋나는 이중 관리 문제에 빠진다.

원칙: 판단은 기존 API가 하게 두고, Gateway는 그 결과를 봇이 이해할 수 있는 형태로 통역만 한다. 미리 규칙을 따져서 막지 않고 일단 기존 처리 API를 호출해보고, 비즈니스 규칙 때문에 거절되면 그 응답을 requiresHandoff: true로 바꿔 사람에게 넘긴다(06장 부분 실패 처리와 동일 패턴). 이러면 Gateway가 그 규칙 자체를 몰라도 된다.

단, 화면(React)에만 있고 API로는 노출되지 않는 규칙은 이 방식으로 못 거른다. 이 경우 ① 백엔드팀에 API로 노출을 요청하거나, ② Gateway가 최소한으로 복제(리스크 인지 + 변경 동기화 프로세스 필요)하거나, ③ 일단 시도해보고 실패시 handoff — 세 선택지 중, 실무적으로는 ③을 기본값으로 하고 실제 문제가 반복될 때만 ①·②로 승격하는 것을 권장한다.

05인증 및 세션 전략

오늘 논의에서 가장 많이 다룬 부분이다. 확인된 사실부터 정리한다.

확인된 사실 4가지

확정
  1. AS접수 생성 같은 처리성 API는 로그인 세션을 전제로 동작한다.
  2. 이 세션은 서버 세션 쿠키 방식이다 (JWT 토큰 방식 아님).
  3. 내부 앱간 호출도 화면용 API와 동일한 API를 쓴다 (서버 전용 API 없음).
  4. 각 단계 API는 stateless — 파라미터만으로 완결된다.

설계: 시스템 계정 + 캐싱된 쿠키 재사용

이 네 가지를 종합하면, Gateway는 AICC 전용 시스템 계정으로 딱 한 번 로그인해서 받은 세션 쿠키를, 이후의 모든 동시 요청에 재사용하면 된다. 요청마다 새로 로그인하지 않는다.

부수 효과 — 처리성 API를 이 시스템 계정으로 호출하면, AS접수 등의 "처리자/등록자" 필드에 자연히 이 계정이 남는다. 별도로 "봇 호출 여부" 필드를 새로 요청하지 않아도, 기존 구조를 그대로 활용해 어떤 건이 봇 처리 건인지 구분할 수 있다.
확인됨 확정 — 백오피스는 세션키/세션정보를 Redis에 저장해 여러 서버 인스턴스가 공유한다. 즉 Gateway가 로그인해서 받은 쿠키는 로드밸런서가 요청을 어느 인스턴스로 흘려보내도 동일하게 인식된다 — 특정 인스턴스에 종속되는 문제는 없다.

06처리성 API 리스크

AS접수처럼 여러 MSA에 걸쳐 데이터를 생성/변경하는 호출은 조회보다 리스크 등급이 다르다.

부분 실패 처리

"고객 확인은 성공, AS접수 생성 단계에서 실패" 같은 상황은 반드시 생긴다. MSA 구조상 여러 앱에 걸친 트랜잭션을 하나로 묶어 롤백하기 어려우므로, 실패 시 사람 상담사에게 핸드오프하는 것을 기본 정책으로 제안한다 (04장의 requiresHandoff 필드 활용).

멱등성 (Idempotency)

봇/네트워크 재시도로 같은 AS접수가 중복 생성되는 걸 막아야 한다. AICC가 넘겨주는 대화/턴 ID를 idempotency key로 활용해 중복 요청을 걸러낸다.

인입 채널 코드

확인 필요

AS접수는 VOC로 등록되며, VOC에는 이미 "통합VOC인입채널코드"라는 출처 공통코드가 있는 것으로 보인다(홈페이지 / 설치마스터앱 / 상담톡 / 상담센터 등). 여기에 AICC/챗봇 값을 추가해달라고 요청하면 VOC 출처 추적에 도움이 된다 — 다만 이건 "호출자 인증/권한" 문제와는 별개이며, 위 시스템 계정 방식이 그 문제를 담당한다.

07설계 우려사항: 조회 API DB 직접 접근

제기된 방향 — 처리성(쓰기) API는 기존 백오피스 API를 그대로 쓰되, 조회성(읽기)은 Gateway가 고객/주문 DB에 직접 접근해 자체적으로 새 API를 구현하는 방향이 검토되고 있다. 확인 필요

결론부터: 이 방향은 지양하는 걸 권한다. 02장에서 확인한 "기존 앱간 호출도 화면용 API를 공유해서 쓴다"는 원칙과도 어긋나고, 아래 세 가지 구체적인 리스크가 있다.

① 비즈니스 로직이 DB 밖(애플리케이션 코드)에 있음

탈퇴 고객, 블랙리스트, 상태값 조합에 따른 필터링 같은 로직이 고객app의 서비스 레이어에 있을 가능성이 높다. Gateway가 DB를 직접 쿼리하면 이 로직을 모른 채 읽게 되어, 상담사 화면에는 안 보이는 고객이 봇에게는 조회되는 식의 불일치가 생길 수 있다. AS접수 흐름에서는 이게 잘못된 고객 정보로 접수가 생성되는 사고로 이어질 수 있다.

② DB 스키마는 고객app 팀의 소유물

테이블/컬럼 구조는 그 팀의 구현 세부사항이다. 리팩터링으로 컬럼명이 바뀌거나 테이블이 쪼개지면 Gateway는 경고 없이 조용히 깨지거나 조용히 틀린 값을 반환한다. API 계약이 있었다면 최소한 변경이 드러나는데, DB 직접 접근에는 그 안전판이 없다.

③ 05장에서 세운 정합성이 깨짐

쓰기는 세션 인증으로 기존 API를 태우는데 읽기만 DB로 직행하면, 한 시스템 안에 완전히 다른 두 통합 방식이 공존한다. DB 자격증명/네트워크 접근/커넥션 풀을 Gateway가 새로 떠안아야 하고, 봇이 무거운 쿼리를 잘못 날리면 상담사들이 실시간으로 쓰는 운영 DB 성능에 직접 영향을 줄 수 있다 — API 뒤에 있었다면 그 앱이 방어막이 되어줬을 부분이다.

추정되는 동기와 대안

아마 "기존 조회 API가 느리다/봇 용도에 안 맞는다" 또는 "다른 팀 일정에 안 막히고 싶다"는 동기일 가능성이 높다. 동기는 타당하지만, DB 직접 접근보다 나은 해법이 있다.

대안 — 고객app/주문app 팀에 "AICC용 경량 조회 API"를 그 도메인 안에 새로 만들어달라고 요청한다. 여전히 API 계약을 통하기 때문에 소유권과 검증 로직이 유지되면서, 봇에 맞게 가볍고 빠르게 최적화될 수 있다. "새 API를 만든다"는 방향 자체는 유지하되, 그 새 API가 Gateway가 아니라 각 도메인 app 안에 생기는 것으로 바뀌는 것이 핵심 차이다.

08확인 체크리스트

다음 미팅에서 확인이 필요한 항목들이다.

상담app / 서비스app 백엔드팀

  • 시스템 계정AICC 전용 계정을 만들 때 UI 로그인은 막고 API 호출만 허용하는 제한이 가능한가?
  • 세션 정책처리성 API들의 세션 타임아웃 기준은 유휴 시간(idle) 기준인가, 절대 시간 기준인가?
  • 공통코드통합VOC인입채널코드에 "AICC/챗봇" 값을 추가할 수 있는가?
  • 모니터링기존 API 모니터링 솔루션이 신규 Gateway 앱에도 그대로 적용되는가? (로깅/모니터링 설계는 이 답이 나온 뒤 진행)

AICC 벤더

  • 인증Gateway와 벤더 간 인증 방식으로 어떤 옵션을 지원하는가? (API Key / OAuth2 / mTLS 등)
  • 네트워크벤더의 발신 IP가 고정되어 있는가?
  • 추적대화/콜 세션 식별자를 요청 헤더로 전달해줄 수 있는가? (04장 traceId)
